# 审查门禁

## 流程

1. 决策智能体提交完整产物和审查材料：原始任务、需求映射、关键假设、证据/数据来源、验证结果、已知限制。
2. 反调审查者独立检查，不先接受提交者的结论。逐条核对用户要求和证据。
3. 审查者将问题按模板交给决策层；不得直接修复被审产物。
4. 决策层可以逐项反驳。反驳必须指出具体审查项，并给出反证或证据链缺口。
5. 审查者只对受质疑项及必要上下文复核，记录支持、修正或撤回及其依据。
6. 所有未解决问题处理完后，审查者给出限定范围的最终状态。执行层仅接收通过的版本及审查记录。

## 单项问题格式

每项发现都必须包含：

- **问题**：具体、可复现的缺陷或未满足要求。
- **证据**：直接支持该判断的来源、代码位置、原始数据、命令输出或计算过程；注明检查时间。
- **影响**：错误会如何影响决策、结果、用户或系统。
- **解决方案**：决策层可以安排的整改方向；不得代替被审者实施。
- **整改对象**：负责修改方案/代码/数据的人或智能体。
- **状态**：待整改、被申辩、复核中、已解决、撤回或有记录的风险接受。

没有证据的担忧只能列为待核验问题，不能断言为事实。只有标题、摘要或接口返回 HTTP 200，不能证明正文、字段、完整性和计算正确。

## 检查清单

### 所有产物

- 逐项映射任务要求，指出缺项、矛盾和超范围承诺。
- 核对关键事实的原始出处、日期、适用范围和上下文。
- 区分观察事实、来源观点和审查者推断；推断需明确标注。
- 检查重要反例、失效条件、边界与不确定性。
- 记录检查范围、实际做过的验证及未覆盖部分。

### 代码

- 搜索被改函数/模块的所有调用方，确认调用契约和返回值影响。
- 检查信任边界输入、类型、缺失/异常字段、空值、日期/单位及错误处理。
- 关注静默错误、错误证券/市场路由、部分数据被当完整、敏感数据泄露和数据损失。
- 读取真实检查结果。没有运行或无法运行时明确标注；不得推断测试通过。
- 不承诺“不会出现 bug”；给出检查过的路径和剩余风险。

### 数据与研究

- 对核心数据记录原始出处、抓取时间、数据时间、单位、口径、过滤与转换。
- 重要数值做算术复算或独立来源交叉核对；来源不一致时说明差异，不能挑选支持结论的一边。
- 区分消息发生、发布时间与预期影响时间。
- 不能独立确认的内容标为待核验，不当作已证实事实。

## 严重程度与放行

严重程度只帮助排序，不改变放行条件：

- **阻断**：可能导致错误决策/标的、资金或数据损失、安全问题，或直接违反任务要求。
- **重大**：核心结论、关键字段、主要行为或来源无法成立。
- **一般**：影响次要、可限定范围的正确性或可用性问题。
- **提示**：纯建议，不构成当前范围内的问题或未满足要求。

只要存在任何未解决的有效问题（无论严重程度），或用户要求的关键证据/验证缺失，状态必须是 **不通过**。不能通过风险接受记录来豁免问题或放行；决策层可以反驳并要求复核，问题成立时必须由责任方整改或弃置产物。通过只能表示“在列明范围内，当前未发现未解决问题”，不表示绝对无缺陷。

最终状态：

- `FAIL`：发现未解决的问题或关键证据缺失。
- `RECHECK`：决策层已对具体条目提出异议，复核未完成。
- `PASS — scoped`：范围、证据和验证均列明，未发现未解决问题；可以提交执行层。

## GitHub 交接

- 用 PR 留存产物、需求映射、来源/验证记录和审查结论。
- CODEOWNERS 只是责任人映射。仓库管理员必须启用并验证 `main` 分支保护、必需代码所有者审查、禁止绕过规则；规则未生效前不能声称 PR 合并受到阻断。
- 文档、模板或自动字段检查本身都不是事实核验。合并、部署或交易权限不应由“材料格式齐全”自动触发。
